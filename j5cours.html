🧱 1) Types avancés : transformer des types comme un architecte

Objets: Utiliser des outils TypeScript qui permettent de créer des types dynamiques, adaptés à la logique métier. 


				
					type Optional<T> = { [K in keyof T]?: T[K]; };
					
					➡️ Tu rends toutes les propriétés optionnelles.
					➡️ C’est comme Partial<T>, mais fait maison.
			    

					type PrefixKeys<T> = {
					  [K in keyof T as `test_${string & K}`]: T[K];
					};
					
					//Si tu as: 
					type User = { email: string; password: string };
					//Tu obtiens :
					{
					  test_email: string;
					  test_password: string;
					}
					➡️ ${string & K}  =  suffixe de la clé.
					➡️ Ultra utile pour générer des structures de test.
			    

					type ExtractStringProps<T> = {
					  [K in keyof T]: T[K] extends string   ?   T[K] : never;
					};

					➡️ Tu filtres les propriétés selon leur type.
					➡️ Très utile pour générer des datasets ou des validations.
🧱 2) Logique métier typée

Objets: Modéliser des règles métier - Règles d’accès(exemple d'accès selon le rôle).


					type Role = "admin" | "user" | "guest";
			    

					type Permissions = {
					  dashboard: boolean;
					  settings: boolean;
					  billing: boolean;
					};
			    

					type RolePermissions = Record<Role, Permissions>;
			    

					const permissions: RolePermissions = {
					  admin: { dashboard: true, settings: true, billing: true },
					  user: { dashboard: true, settings: false, billing: false },
					  guest: { dashboard: false, settings: false, billing: false }
					};
					➡️ Tu peux maintenant écrire des tests qui s’adaptent automatiquement au rôle.
🧱 3) Tests paramétrés (Playwright Pro)

Objets: écrire des tests qui tournent plusieurs fois, avec des données différentes, sans dupliquer le code. 


					// test( `nomTest`, async({page})  => {actions, permissions} );
					
					const roles = ["admin", "user", "guest"] as const;

					for (const role of roles) {
						test(`access for ${role}`, async ({ page }) => {
							// test action(s)
							await page.goto("/dashboard");
							// test permission
							const canAccess = permissions[role].dashboard;
							if (canAccess) {
							  await expect(page).toHaveURL(/dashboard/);
							} else {
							  await expect(page).toHaveURL(/login/);
							}
						});
					}
					➡️ const = empêche de réassigner la variable roles.Mais les elt de la liste("admin", "user", "guest") restent modifiables.
					➡️ ${role} = le role à tester: choisi parmis la liste  roles 
					➡️ 3 tests générés automatiquement.
					➡️ Logique métier + dataset + test paramétré.
🧱 4) Tests paramétrés avec fixtures + Page Objects

Objets: Test générique - Plusieurs paramètres à la fois( utilisateur, son rôle, etc ...) 


					const users = [
					  { email: "admin@test.com", password: "123456", role: "admin" },
					  { email: "user@test.com", password: "123456", role: "user" }
					] as const;

					for (const u of users) {
					  test(`login test for ${u.role}`, async ({ loginPage }) => {
						// test actions
						await loginPage.goto();
						await loginPage.email.fill(u.email);
						await loginPage.password.fill(u.password);
						await loginPage.submit.click();
						
						// test permissions
						const canAccess = permissions[u.role].dashboard;
						if (canAccess) {
						  await expect(loginPage.errorMessage).toBeHidden();
						} else {
						  await expect(loginPage.errorMessage).toBeVisible();
						}
					  });
					}
					➡️ Tu génères des tests dynamiques.
					➡️ Tu relies types, dataset, logique métier, fixtures, Page Objects.
					C’est du Playwright niveau ingénieur QA.
			    

					Les données ne sont pas persistées dans la base( comme chez symfony).
					Pas de base de données dans les tests.
					Tu crées des objets en mémoire, souvent des tableaux, des maps, des datasets typés.
					Ces données servent à piloter tes tests (login, rôles, permissions, scénarios).
					
					Dans tous les cas la fixture est un jeu de données factice. Elle reste:
					  🔹 un jeu de données
					  🔹 typé
					  🔹 immuable
					utilisé pour générer des tests dynamiques,
					consommé par ton code de test

					// Exemple précedent:
					const users = [
					  { email: "admin@test.com", password: "123456", role: "admin" },
					  { email: "user@test.com", password: "123456", role: "user" }
					] as const;
					➡️ Ici, const users = [...] as const est une fixture.
					➡️ Mais une fixture en mémoire, pas une fixture en base comme dans Symfony.
🧱 5) Bonus : Tests paramétrés typés

Objets: Typer les données du test( pour éviter les erreurs). 


					// 5.1 Le type
					interface LoginScenario {
					  user: TestUser;
					  expectedSuccess: boolean;
					}

					// 5.2 La fixture
					const scenarios: LoginScenario[] = [
					  { user: users.admin, expectedSuccess: true },
					  { user: users.user, expectedSuccess: true },
					  { user: users.guest, expectedSuccess: false }
					];

					// 5.3 Le test
					for (const s of scenarios) {
					  test(`login scenario for ${s.user.role}`, async ({ loginPage }) => { // LoginPage 👉  Cf J4/Cours/4.2
						await loginPage.goto();
						await loginPage.email.fill(s.user.email);
						await loginPage.password.fill(s.user.password);
						await loginPage.submit.click();

						if (s.expectedSuccess) {
						  await expect(loginPage.errorMessage).toBeHidden();
						} else {
						  await expect(loginPage.errorMessage).toBeVisible();
						}
					  });
					}
					➡️ Tu as un framework de tests paramétrés.
					➡️ Tu peux ajouter des scénarios sans toucher au code du test.

Objectif: Inventer des types (puissants, réutilisables, propres)

1. Les types utilitaires:

  • ✔ Partial<T>
  • ✔ Required<T>
  • ✔ Readonly<T>
  • ✔ Pick<T>
  • ✔ Omit<<T>
  • ✔ Record<T>
  • ✔ ReturnType<T>

permettent de tranceformer des types existants.
👉 Ce sont les “super‑pouvoirs” de TypeScript.

2. Les génériques

function identity<T>(value: T): T { ... }
  • ✔ ça permet d'inventer des types flexibles
  • ✔ ça évite les répétitions
  • ✔ ça améliore la sécurité du code

C'est pour de tranceformer des types existants.
👉C’est le cœur du TypeScript moderne.

3. Generic Interfaces & Types

On parle d'Interfaces génériques avancées et de types paramétrés

Comment écrire :

  • interface ApiResponse<T> {
  •  data: T;
  •  status: number;
  • }

Et comment les utiliser avec :
 → Des types complexes, des objets,
 → des tableaux, des fonctions
👉 C’est ce qui permet de modéliser des réponses API, des actions Playwright📌, etc.

4. Fonctions typées avancées

Il y en a 3 fonctions typées:
  • ✔ Les fonctions génériques,
  • ✔ celles retournant des types complexes
  • ✔ celles qui manipulent des objets typés
  • ✔ et les signatures de fonction

👉 Ça te prépare directement à Playwright,
car Playwright utilise énormément de types complexes.
